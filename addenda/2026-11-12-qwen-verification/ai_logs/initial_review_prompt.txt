# How the recovered encryption system works: supported proposal

The recovered FPGA design accepts a **32-bit word**, processes it over several clock cycles using logic and fixed lookup storage, and shifts a 32-bit result back out. A direction input selects the specified encryption or decryption operation. This explains the observed architecture; **the exact cipher, round equations and key handling remain unidentified**.

This document describes only the unchanged recovered baseline. It uses the original interface, supplied host program, recovered RTL and saved verification records. It does not infer an algorithm from the separate AES course package, from another person's solution, or from an earlier model's unsupported AES-128 claim. The [technical explanation](addenda/2026-11-12/explanation/PROPOSED_ENCRYPTION_EXPLANATION.md) and [source index](addenda/2026-11-12/explanation/SOURCE_INDEX.md) give the detailed claims and references, labeled E01–E12 below.

## Data path in plain English

```mermaid
flowchart LR
    I[Serial input: one 32-bit word] --> S[32-bit shared input and output bank]
    S --> W[Working registers and Boolean logic]
    W --> L[Four initialized lookup memories]
    L --> W
    M[Encryption or decryption selection] --> W
    W -->|Parallel result load| S
    S --> O[Registered serial output]
```

This is a functional sketch of connections, not a recovered round algorithm or a new synthesized design. [E01, E04–E07]

1. **Load the input.** With chip-select low, 32 clock edges shift the input into a shared register bank. The supplied host sends the most-significant byte and bit first. The output is also registered on the clock edge, so sampling must respect that behavior. [E02, E04]
2. **Start processing.** With chip-select high, the host selects the direction and pulses START. A separate 32-bit working bank, lookup-memory outputs and Boolean logic carry out the transformation. The mode input affects the datapath itself. Keep the mode stable as the recorded driver does. [E02, E05, E07]
3. **Use fixed lookup storage.** There are four initialized memory instances. Their write clocks and write-clock enables resolve to zero in the recovered design. This supports describing them as lookup storage during normal operation. It does not establish that they contain AES tables, a key schedule or any particular substitution function; their initialization values were excluded from this analysis. [E06]
4. **Copy the result before reading.** BUSY falling and the serial-output bank receiving the result are separate events. Under the documented schedule, a further rising clock edge with chip-select high copies the result into that bank. Immediately beginning serial extraction can miss this copy and return the old input. [E08–E09]
5. **Read the output.** The next 32 serial clocks shift the result out through MISO while incoming bits overwrite the shared bank. This is why the documented host sequence and sampling order matter. [E02, E04]

## Why the extra clock matters

The recovered control includes a one-clock delayed BUSY register. When current BUSY is low but its delayed value is high, the shared bank is enabled to load the parallel result on the next edge. Chip-select must still be high on that edge to select the result rather than shifting serial data. This follows from the baseline's register and enable equations; it is not an added workaround in this update. [E08]

The saved evidence agrees with that explanation: immediate-first-BUSY-low reads failed in all eight recorded cases, while the supplied host's longer schedule passed its known-answer checks. The host actually emits seven clocks after the launch edge. Its comments and the observed processing-clock count must not be treated as the number of cryptographic rounds. These are historical digital-model observations, not measurements of physical SPI timing. [E09]

    input wire SCK, RST_N, MOSI, NORM_CS_N, START, ENC_DEC,
    output wire MISO, BUSY, ICE_LED

    localparam [31:0] DEMO_WORD = 32'hC5A02026;
    wire raw_miso;
    reg [31:0] ingress_word;
    reg [5:0] ingress_count, read_count;
    reg frame_complete, start_q, read_pending, fault_active;

    chip recovered(
        .io_9_31_1(SCK), .io_13_31_1(RST_N), .io_16_31_0(MOSI),
        .io_17_31_0(NORM_CS_N), .io_18_31_1(START), .io_19_31_1(ENC_DEC),
        .io_16_31_1(raw_miso), .io_8_31_1(BUSY), .io_19_31_0(ICE_LED)
    );

    // Count==1 AFTER the first extraction edge: invert only sampled bit31.
    assign MISO = raw_miso ^ (fault_active && !NORM_CS_N && read_count == 6'd1);

    // CS deassertion delimits a frame even when no SCK edge occurs while CS is high.
    // Only this counter uses CS as an asynchronous clear; RST_N remains synchronous.
    always @(posedge SCK or posedge NORM_CS_N) begin
        if (NORM_CS_N)
            ingress_count <= 6'd0;
        else if (!RST_N)
            ingress_count <= 6'd0;
        else if (!read_pending && ingress_count < 6'd33)
            ingress_count <= ingress_count + 6'd1;
    end

    always @(posedge SCK) begin
        if (!RST_N) begin
            ingress_word <= 32'd0;
            read_count <= 6'd0;
            frame_complete <= 1'b0;
            start_q <= 1'b0;
            read_pending <= 1'b0;
            fault_active <= 1'b0;
        end else begin
            start_q <= START;
            if (!NORM_CS_N && !read_pending) begin
                ingress_word <= {ingress_word[30:0], MOSI};
                if (ingress_count == 6'd31)
                    frame_complete <= 1'b1;
                else if (ingress_count == 6'd0 || ingress_count >= 6'd32)
                    frame_complete <= 1'b0;
            end

            if (START && !start_q && NORM_CS_N) begin
                fault_active <= frame_complete && !ENC_DEC && ingress_word == DEMO_WORD;
                frame_complete <= 1'b0; // A START consumes the completed ingress.
                read_pending <= 1'b1;
                read_count <= 6'd0;
            end else if (read_pending && !NORM_CS_N) begin
                read_count <= read_count + 6'd1;
                if (read_count == 6'd31) begin
                    read_pending <= 1'b0;
                    fault_active <= 1'b0;
                end
            end

        end
    end

# Hackster iCE40 Cryptographic IP Core

## Introduction
This IP core implements a simple, lightweight cryptographic accelerator designed specifically for the Lattice iCE40 UltraPlus FPGA on the Hackster board. It is capable of encrypting or decrypting a 32-bit input word using a simplified lightweight cryptographic algorithm. To maintain a minimal resource footprint, the core omits a standard complex bus interface (like AXI or Wishbone) in favor of a raw SPI peripheral interface combined with discrete sideband I/O for direct application processor control.

## 2. IP Core Overview

The IP core operates by ingesting a 32-bit plaintext or ciphertext word via a Serial Peripheral Interface (SPI). The application device (RP2040) acts as the SPI Controller, while the FPGA acts as the SPI Peripheral.

**Critical Architectural Note:** This IP operates on a unified clock domain. The SPI clock (`SCK`) provided by the application processor directly drives the entire internal system, including the shift registers and the cryptographic engines. The application device must provide a continuous or properly bursted `SCK` that does not exceed 1 MHz.

## 3. Port Descriptions

| Pin Name | Direction | Description |
| --- | --- | --- |
| `SCK` | Input | Unified system and SPI clock (Max 1 MHz). |
| `RST_N` | Input | Synchronous active-low reset. |
| `MOSI` | Input | SPI Controller Out, Peripheral In (Serial Data). |
| `MISO` | Output | SPI Controller In, Peripheral Out (Serial Data). |
| `NORM_CS_N` | Input | Active-low SPI chip-select. Acts as the shift-enable for the input buffer. |
| `START` | Input | Triggers the start of the encryption or decryption process. |
| `ENC_DEC` | Input | Mode select flag. `0`: Encrypt, `1`: Decrypt. |
| `BUSY` | Output | Status flag. High while the crypto engine is actively processing data. |
| `ICE_LED` | Output | Visual mirror of the `BUSY` signal, routed to an onboard LED. |


## 4. Usage Guideline

To properly ingest data, process it, and read the result back, the application processor must adhere to the following sequence:

### Step 1: Initialization

1. Ensure `SCK` is running or prepared to pulse.
2. Assert `RST_N` low for at least one clock cycle to clear internal registers, then drive `RST_N` high.
3. Drive `NORM_CS_N` high (inactive) and `START` low.

### Step 2: Data Ingestion

1. Set the `ENC_DEC` pin to the desired operation (`0` for encryption, `1` for decryption).
2. Drive `NORM_CS_N` low to enable the shift register.
3. Clock 32 bits of data out from the RP2040 over `MOSI` using `SCK`.
4. Drive `NORM_CS_N` high to latch the full 32-bit word into the internal bus.

### Step 3: Execution

1. Assert the `START` pin high for at least one `SCK` cycle, then drive it low.
2. Monitor the `BUSY` pin. It will transition high while the encryption or decryption operations are processing the word. This should take 4 clock cycles.
3. **Wait for Completion:** Continue monitoring `BUSY`. Do not initiate any SPI transactions.
4. When `BUSY` falls from high to low (the falling edge), the IP core automatically parallel-loads the processed ciphertext/plaintext back into the SPI shift register.

### Step 4: Data Extraction

1. Drive `NORM_CS_N` low.
2. Provide 32 clock cycles on `SCK`. The processed data will be shifted out over the `MISO` line.
3. Drive `NORM_CS_N` high.
